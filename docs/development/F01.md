# F01 — publish one ready file

`phase publish-file` and MCP `phase_publish_file` call the same
`PhaseApplication.publish_file` → `phase_tool.publish_file.publish_file`.
No naming conflict. No Hermes/profile/checkout dependency or internal LLM call.

## Interface and scope

Required arguments (CLI uses `--kebab-case`, MCP uses `snake_case`):
`source_root`, `source_locator`, `target_root`, `target_locator`,
`preparation_root`, `evidence_root`, `request_id`, `run_id`.
Optional `expected_digest`: exact lowercase `sha256:<64 hex>`.
Source, target and preparation roots must already be directories; evidence may
be new. All four roots must be mutually disjoint after normalization, with no
symlink/reparse components. Locators use the existing safe relative-path policy
(no dot-path exceptions); target parents must already exist. Request IDs follow
the existing operation ID syntax (lowercase, at most 128 characters). Run IDs
retain the existing evidence namespace rules.

One existing regular file of arbitrary bytes, **0..1,048,576 bytes inclusive**.
No decoding, JSON interpretation, archive expansion, content edits, replacement,
version publication, bundles or streaming. The source capture is bounded by the
minimum existing exclusive-create and independent-inspect limits (both 1 MiB),
not the 16 MiB freeze limit. The generated structured candidate is metadata only
and remains subject to the application's 1 MiB candidate admission limit.
Growth during capture cannot evade the bound: existing stable capture reads at
most limit+1 and detects stat/identity drift. Expected digest is checked against
captured bytes. Without one, the accepted bytes are fixed by that stable
`copy_and_hash` capture, not by initial stat or later source reads.

## Lifecycle and evidence

Private temporary preparation under `preparation_root` uses existing freeze and
revalidation, then passes the captured blob into the existing exact-bound
`PhaseApplication.run("execute")` lifecycle. The bundled registry resolves
`file_create.v1@1.0.0` with its exact current package digest
`sha256:e3231b5f97bb49c499a82fd1d003ddde081c9cbe31b7b10b87435526c1e15870`;
the operation records that digest and uses `phase_result_root` for inspect.
This existing product contract supports the create scenario, so no new
contract/package is needed. Supported execution is Linux on a qualified
ext4/overlay filesystem; editing on Windows does not qualify Windows mutation.
Core re-freezes the staged input, plans, writes intent and executes only through
the existing broker/mechanism. Exclusive creation enforces absence **at commit**,
not just at preflight. Existing target never selects another operation.

Success additionally requires independent `PhaseApplication.inspect`, matching
run/disposition/mutation flags and all execute/inspect digests, plus authenticated
intent/candidate/request/contract and single-effect target/content correspondence.
Detailed intent, frozen blobs, plan and receipt remain in
`evidence_root/.phase/runs/<run_id>/`. No additional acceptance publication.

## Result and failures

`PublishFileResult` is a strict, closed Pydantic model with JSON Schema via
`model_json_schema()`, version `publish_file_result_version="1.0"`; MCP advertises
it as outputSchema. No historical closed schema is changed. The compact result
contains no file contents or full logs.

- `verified` / exit 0: durable receipt, independently verified target and matching
  request evidence.
- `rejected_before_write` / exit 10: current invocation rejected without target
  mutation; this does not assert that a previous invocation never wrote.
- `committed_unverified` / exit 30: execution reported a completed result but
  independent inspection/correlation failed. Preserve run and available digests;
  do not treat this as “not executed”.
- `indeterminate` / exit 40: handoff/outcome/finalization cannot establish the
  completed state. `mutation_attempted=null` means unknown, not false.

Existing Core idempotency remains authoritative, including its freeze-time
request binding. F01 deliberately chooses exact refusal rather than promising
automatic reuse: an existing target yields
`publish_file.target_exists_inspection_required`; an occupied run ID yields
`evidence.run_exists`/indeterminate. `inspection_required=true` directs the caller
to inspect existing evidence. No new key, timestamp substitution, physical
rewrite, automatic resume or new idempotency system is introduced. Commit-time
exclusive creation still protects races after the preliminary absence check.
