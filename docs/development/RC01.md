## Design and verification checkpoints

1. **F02 streaming:** extend the shared publish-file application path with an
   explicit versioned streaming route; the default F01 v1 route and its 1 MiB
   contract stay compatible. New contract/mechanism bindings are exact. Metadata
   stays bounded separately from payloads. Stream capture, frozen validation,
   broker transfer, writer, post-validation and independent inspect end-to-end.
   Target creation remains create-only with commit-time absence enforcement.
   Streaming limits: 1 MiB canonical request, 2 GiB/file, one file per operation,
   one executor and one active high-level operation per target root. Bound actual reads/writes, not only initial stat. A stable-stat
   capture fixes consumed bytes but is **not** an atomic snapshot of an
   arbitrarily mutable source. Gates: old/new boundaries, real 1 GiB I/O,
   isolated-process peak RSS delta (64 MiB to 1 GiB) <=128 MiB; record time and
   disk costs. No threshold relaxation.
2. **F03 bundles:** finite explicit safe relative paths, member lengths/digests,
   digest-bound canonical membership, full byte verification. Stage locally and
   expose one final create-only bundle commit point; no cross-resource
   transaction claim. Proposed bounds: 1024 members, 4 GiB total, 2 GiB/member,
   1 MiB request, one executor. Gate: >=256 files / >=256 MiB; missing/corrupt/
   duplicate/unsafe entries and interruption before commit cannot verify.
   Implement a legacy reader only for an exact locally evidenced format; absence
   of such a sample is NOT_VERIFIED, never invented compatibility.
3. **F04 recovery:** retain exact request, frozen inputs, intent and effect
   evidence. Explicit status/verify/recover; never silently reread changed inputs,
   change idempotency keys, or rewrite proven completed targets. Classify crash,
   partial write/ENOSPC, post-effect inspect/finalization failure, lost response,
   replay/conflict and concurrent targets. Only proven own unneeded temporaries
   may be removed. No generic workflow engine.
4. **F05 integration:** shared CLI/MCP implementation for files/bundles; compact
   responses and path references, no payload bytes in LLM context. Fast saved
   status is distinct from full current verification. Programmatic wait/progress
   and timeout reconciliation without a queue server. Test installed real MCP
   stdio and cross-transport inspect. Add a concise integration example.
5. **F06 candidate:** retain V1/F01 safety tests; exact-head Linux Python 3.11/3.12
   regression, dedicated mandatory resource job, wheel/sdist, isolated noneditable
   installed candidate, historical evidence verification, release notes, rollback
   instructions and maintainer handoff. Target additive prerelease `1.1.0rc1`,
   subject to executable version compatibility. Candidate artifacts live outside
   checkout under `ROOT/artifacts/RC01/<version-and-commit>`; evidence under
   `ROOT/evidence/RC01/<checkpoint>`. PR #2 describes the complete scope.

These are implementation decisions and gates, not claims of passing tests.

## F02 operational notes

Select `--publication-version 2.0` / MCP `publication_version="2.0"` explicitly;
otherwise the preserved F01 1 MiB route is used. `phase_tool.streaming.limits()`
returns the implemented limits without source parsing. All bytes remain local.
Ordinary files stay ordinary files; create-only does not promise atomic file
visibility while writing. Consumers require verified completion, not existence.

The final local resource report is `ROOT/evidence/RC01/F02-local-report.json`.
The source fixture is written and fsynced outside the measured child; its
allocated blocks are checked (no sparse main workloads). Each child runs one
publication plus an extra independent inspect. Linux `ru_maxrss` is measured;
`/proc/self/io` distinguishes logical bytes from physical storage reads/writes.
Zero physical reads can mean page-cache hits, not omitted content verification.

For input size S, measured operation writes are approximately 3S (preparation,
Core frozen evidence, target), excluding initial source generation. After cleanup,
retained source+evidence+target are approximately 3S. A 4S peak-live layout is a
derived upper-layout estimate, not a sampled disk-peak measurement. Generated
resource fixtures are disposable; command logs, digests and measured counters
are retained. The 1 GiB and exact 2 GiB boundary both passed full content checks.
