## F02 operational notes

Select `--publication-version 2.0` / MCP `publication_version="2.0"` explicitly;
otherwise the preserved F01 1 MiB route is used. `phase_tool.streaming.limits()`
returns the implemented limits without source parsing. All bytes remain local.
Ordinary files stay ordinary files; create-only does not promise atomic file
visibility while writing. Consumers require verified completion, not existence.

The final local resource report is `ROOT/evidence/RC01/F02-local-report.json`.
The source fixture is written and fsynced outside the measured child; its
allocated blocks are checked (no sparse main workloads). Each child runs one
publication plus an extra independent inspect. Linux `ru_maxrss` is measured;
`/proc/self/io` distinguishes logical bytes from physical storage reads/writes.
Zero physical reads can mean page-cache hits, not omitted content verification.

For input size S, measured operation writes are approximately 3S (preparation,
Core frozen evidence, target), excluding initial source generation. After cleanup,
retained source+evidence+target are approximately 3S. A 4S peak-live layout is a
derived upper-layout estimate, not a sampled disk-peak measurement. Generated
resource fixtures are disposable; command logs, digests and measured counters
are retained. The 1 GiB and exact 2 GiB boundary both passed full content checks.

## F03 representation and consumer boundary

`publish-bundle` (`--member` repeated) and `phase_publish_bundle` share
`PhaseApplication.publish_bundle` → the existing Core lifecycle. Members are a
finite set sorted by UTF-8 path bytes. The exact `bundle_create.v1@1.0.0` package
is `sha256:c24023f54bf7a787e5030d63591ed17a4befa3cf6b4de11ab889d454d5a6846c`.
It uses the mechanism-managed `mechanism.bundle_create_v1`; the explicit empty
provider-guarantee requirement mapping does not borrow provider guarantees for
its directory commit. Linux qualified ext4/overlay and native renameat2 are used.

The canonical `phase-bundle.json` (bundle_version 1.0) lists sorted paths, lengths,
member SHA-256 and total_length; its byte digest is the bundle identity. Each
member is separately frozen and recursively verified, not serialized into JSON.
`phase-owner.json` binds the run, plan and staged directory inode. Both names are
reserved at bundle top level; paths retain the strict local policy, depth <=32.
Bounds are conjunctive: <=1024 members, <=2 GiB/member, <=4 GiB payload total,
<=1 MiB request/manifest and one active high-level operation per target root.

Private same-parent `phase-stage-<digest>` directories may physically exist before
publication. A successful `renameat2(RENAME_NOREPLACE)` is the sole atomic consumer
visibility point; parent fsync and full independent verification additionally gate
verified success. Staged members alone never mean publication. Receipt state length
is manifest-byte length; the high-level result separately reports total_length.
Partial staging is retained for explicit F04 reconciliation, not auto-deleted.
The bundle is not an atomic snapshot of arbitrarily changing source files, nor
an external-resource transaction. Ordinary publish-file results remain files.

Exact legacy chunks/reassembly compatibility is NOT_VERIFIED, not PASS; bounded
source searches are recorded in `ROOT/evidence/RC01/legacy-search.json`. This new
bundle format is not a guessed legacy chunk protocol.

## F04 explicit recovery boundary

`PhaseApplication.recover_publication` takes the original run, request key,
target root and exact expected intent digest. It never recaptures a source,
changes an idempotency key, deletes staging/evidence, or replays a target effect.
It revalidates original exact contract/plan/root identity, frozen bytes and current
target bytes, then writes an immutable `recovery_result_version=1.0` observation
under the original run's `recovery/<byte-sha256>.json`. Original receipt statuses
remain unchanged; `verified_existing` is a **new current observation**, not a
retroactively invented `succeeded_verified` receipt or proof of power-loss durability.

Completion recovery covers lost client responses, transient inspect failure and
missing final receipts after a proven effect. A file requires a valid recorded
`applied_verified` effect plus current byte verification. A bundle additionally
has its run/plan/inode owner marker and recursive member verification, including
when a real process exits immediately after the publication syscall. Conflicting
keys/intents, changed roots, corrupt evidence/targets, unavailable observations,
pre-intent crashes and incomplete/unpublished staging return explicit non-success.

The exact original contracts have `recovery.policy=none`: **no automatic target
repair, staged-directory commit retry or partial-file append is authorized by
this observer**. Safe recovery here restores proven completion/finalization only;
otherwise it retains the precise refusal and all physical/evidence state. This
is a deliberate conservative boundary, not a general resumable-transfer engine.
