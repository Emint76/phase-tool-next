# Connected native file-create candidate: implementation and acceptance boundary

This is an unqualified development candidate. It adds a connected first subset
to the existing Phase Core; it is not an NTFS support announcement. The fixed
candidate registry contains no production native authority profile. Its factory
must refuse before constructing a channel, observing NTFS or reserving evidence.
Ordinary CLI/MCP defaults and the qualified ext4 route remain unchanged.

## One lifecycle, one result owner

The original Docker Desktop 9p transport remains UNSUPPORTED for the demonstrated
NOREPLACE primitive: its EINVAL counterexample is retained. No 9p allowlist or
provider substitution is added. The separately authorized native role performs
the whole NTFS effect. Linux Core still captures/freezes inputs, constructs the
plan and original intent, uses existing validators/idempotency, classifies the
outcome and owns the EvidenceStore and receipt. Result bytes stay on NTFS;
preparation and execution evidence stay in separate owned ext4 roots (MIX).

The logical `exclusive_create_v1` mechanism and existing contract JSON are reused
unchanged. A new immutable candidate snapshot/package includes the additional
evidence schemas. Both older file-create package generations, default registry,
historical descriptors and public schemas retain their original bytes.

No PENDING/FINALIZED journal, shared queue, document-history index, parallel
recovery engine or second version store is introduced. Intent, idempotency,
receipt, recovery barriers and contract validators remain the existing owners.
Optional history indexing and higher array/file limits are separate issues.

## First subset and honest evidence levels

The first implementation subset is existing `file_create.v1`, one exclusive
effect, existing parents and a frozen payload of at most 1 MiB. This does not
implement or qualify version updates, bundles or all six required contracts.
Control-frame bounds are metadata bounds, not a new promise for large assets.
No product limit or contract semantics are increased to make qualification pass.

Source review has caught and corrected: a planned-original artifact filename
mismatch; lost primary Broker errors on late preparation failures; diagnostic
formatting that discarded a valid partial receipt; blocking startup framing;
unsafe inference of absence after an opened directory disappeared; and a broad
AST import exemption. Rejected drafts are retained in the private Phase evidence
chain. Source review and component tests must not be presented as native lifecycle
execution or transport qualification.

The component regression sources cover actual ext4 evidence IO and immutable
failure attachment, per-file/directory fsync faults, primary/secondary cleanup,
planned-original reading, fixed registry history, candidate refusal and bounded
uncertainty. Synthetic receipt/proof files in IO tests explicitly grant no
authority. No successful profile/provider/qualification replacement is used.
Actual execution results belong to the precise CI HEAD/build; this document does
not predeclare them passed.

Future execution must use an explicitly owned isolated installation, exact
reviewed launcher/runtime/wheel/registry/environment identity, independent
observers and the unchanged qualification program. No production Hermes/Phase
configuration, policy, privilege, scientific data or canonical volume is changed.
The candidate stays draft and unqualified until all mandatory checks pass.

Software preservation and review can proceed while unavailable safety checks
remain NOT_VERIFIED. Merge, supported NTFS claims and release cannot.
